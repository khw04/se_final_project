# Pokemo 개인정보 처리 및 보안 정책

## 목적

이 문서는 Pokemo MVP 제출/시연 범위에서 수집하는 개인정보, 저장 방식, 접근 통제, 보안 한계와 후속 보강 계획을 정리한다.

## 수집 항목

| 구분 | 항목 | 목적 |
| --- | --- | --- |
| 계정 | 이메일 | 회원 식별, 로그인, 이메일 인증, 비밀번호 재설정 |
| 인증 | 비밀번호 해시 | 이메일/비밀번호 로그인 검증 |
| OAuth | OAuth provider, provider user id | Google/Kakao 로그인 계정 연결 |
| 학습 데이터 | 과목, 일정, 노트, 퀴즈 풀이 이력, 오답, 공부 시간 | 학습 관리 기능 제공 |
| 첨부파일 | 노트 이미지 파일 | 노트 이미지 첨부 기능 제공 |
| 알림 | 웹 푸시 구독 endpoint/key | 일정 임박 웹 푸시 알림 발송 |

주민등록번호, 결제 정보, 주소, 전화번호 등 민감하거나 과제 범위에 불필요한 개인정보는 수집하지 않는다.

## 저장 및 보호 방식

- 비밀번호는 원문 저장 없이 BCrypt 해시로 저장한다.
- Access Token과 Refresh Token을 분리하고, Refresh Token은 서버 DB에 저장한다.
- Refresh Token은 로그아웃 시 revoke 처리하고, refresh 성공 시 기존 토큰을 revoke한 뒤 새 토큰을 발급한다.
- 운영 통신은 DuckDNS/Caddy 기반 HTTPS를 사용한다.
- 운영 DB는 AWS RDS MySQL을 사용하며, 애플리케이션은 환경변수 기반 DB 접속 정보를 사용한다.
- 첨부파일은 운영 환경에서 EC2 IAM Role 기반 S3 저장소에 저장한다.
- 비밀번호 해시는 사용자 프로필과 분리된 `Credential` 엔티티(`credentials` 테이블)에 저장한다.
- 운영 DB 연결은 `VERIFY_IDENTITY` TLS를 기본으로 사용해 전송 구간을 보호하고 서버 인증서를 검증한다.
- 보안 감사 로그에는 이메일을 마스킹(`s***@example.com`)해 기록하고, 사용자 추적은 내부 `userId`로 수행한다.
- Gemini, OAuth, SMTP, JWT secret, VAPID private key 등 비밀값은 `.env`/배포 환경변수에만 저장하고 Git에 커밋하지 않는다.
- 프론트엔드는 OAuth public client id만 포함하고 provider secret은 백엔드/배포 환경에만 둔다.

## 접근 통제

- 일반 API는 JWT 인증 후 접근한다.
- 관리자 API와 공지 작성/수정/삭제는 `ADMIN` role만 허용한다.
- 공지 목록/상세 조회, health check, Swagger 문서, 첨부파일 GET 등 공개가 필요한 일부 경로만 인증 없이 허용한다.
- 프론트 Nginx `/api/` 프록시에서 `Authorization` 헤더를 백엔드로 전달한다.

## 보존 및 삭제 정책

- MVP 범위에서는 계정 삭제 자동화 API를 제공하지 않는다.
- 사용자가 생성한 과목, 일정, 노트, 태그, 첨부파일, 퀴즈 데이터는 서비스 기능 제공을 위해 저장한다.
- 노트, 태그, 일정, 공지 등 주요 사용 데이터는 화면 또는 API에서 삭제할 수 있는 범위 내에서 삭제한다.
- 제출 이후 운영 수준에서는 계정 탈퇴, 데이터 일괄 삭제, S3 첨부파일 정리, 백업 보존 기간 정책을 추가로 정의해야 한다.

## 현재 한계 및 결정

- 브라우저 인증 세션은 MVP 범위에서 `localStorage['pokemo.auth']`에 Access/Refresh Token을 저장하는 방식을 유지하기로 결정했다.
- `localStorage` 방식의 XSS 토큰 탈취 위험은 CSP 보안 헤더, `dangerouslySetInnerHTML` 미사용, Access Token 단기 TTL과 Refresh Token rotation/revoke로 완화한다. 운영 상용 서비스 수준에서는 HttpOnly Secure Cookie 또는 BFF 패턴 전환을 검토한다.
- 현재 인증 방식은 Authorization Bearer header 기반 stateless API이므로 CSRF 위험이 구조적으로 낮아 CSRF를 비활성화했고, 이는 현재 모델에 부합하는 설정이다. 쿠키 기반 인증으로 전환할 경우에만 SameSite cookie와 CSRF token 정책을 함께 도입한다.
- 이메일, 노트 본문 등 일반 데이터에 대한 필드 단위 암호화는 적용하지 않았다(전송 구간은 HTTPS/DB TLS로 보호).

## 후속 보강 계획

- HttpOnly Secure Cookie 또는 BFF 기반 인증 구조 검토
- 쿠키 기반 인증 전환 시 CSRF token 적용
- 계정 탈퇴 및 사용자 데이터 일괄 삭제 API 추가
- 백업 보존/복구 정책 수립
- 관리자 승격/삭제 등 민감 운영 작업 감사 로그 강화
- 운영 RDS SSL `VERIFY_IDENTITY` 적용 및 CA 검증 절차 문서화
