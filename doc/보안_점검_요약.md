# Pokemo 보안 점검 요약

## 적용 완료

- 비밀번호 저장: BCrypt 해시 적용
- 인증 구조: JWT Access Token과 Refresh Token 분리
- Refresh Token: DB 저장, 로그아웃 시 revoke 처리
- 권한 제어: `USER`/`ADMIN` Role 구분, `/api/admin/**` 및 공지 변경 API ADMIN 제한
- 이메일 인증: 미인증 계정 로그인 차단
- CORS: 허용 origin을 환경변수로 제한
- SQL Injection: 주요 데이터 접근은 Spring Data JPA Repository 기반으로 처리
- XSS 기본 방어: 프론트엔드는 React 렌더링을 사용하며 `dangerouslySetInnerHTML` 사용 없음
- 보안 헤더: CSP, Referrer-Policy, Permissions-Policy, X-Frame-Options, HSTS 설정
- 인증 실패 로그: 로그인 실패, 미인증 로그인 차단, JWT 검증 실패 로그 기록
- 보안 로그 PII 마스킹: 로그인 감사 로그의 이메일을 `s***@example.com` 형태로 마스킹(`common/LogMask`), 추적은 내부 `userId`로 수행
- 접근 제어 강화: 과목 데이터를 사용자별로 분리하고 공부 세션 생성 시 과목 소유권을 검증
- 자격 증명 분리: 비밀번호 해시를 `Credential` 엔티티로 분리 저장
- DB 전송 보안: 운영 RDS 연결 `VERIFY_IDENTITY` 기본화 및 RDS CA truststore 적용 절차 문서화
- 개인정보 최소 수집 정책: 이메일, 학습 데이터, 첨부파일, 웹 푸시 구독 정보 등 서비스 제공에 필요한 항목만 수집하도록 문서화
- OWASP Top 10 간단 점검표 작성: 적용 통제와 후속 보강 범위 구분

## 현재 정책 설명

- 브라우저 토큰 저장은 `localStorage` 기반을 유지하기로 결정했다(MVP 범위). Authorization Bearer header 기반 stateless API라 브라우저가 인증정보를 자동 첨부하지 않으므로 전통적 CSRF 위험은 구조적으로 낮다.
- 따라서 CSRF는 Spring Security에서 비활성화한 상태가 현재 인증 모델에 부합하는 올바른 설정이다. 추후 쿠키 기반 인증으로 전환할 경우에만 SameSite cookie와 CSRF token을 함께 도입한다.
- `localStorage` 방식의 XSS 토큰 탈취 위험은 다음 완화책으로 줄인다: CSP 보안 헤더, `dangerouslySetInnerHTML` 미사용, Access Token 단기 TTL(기본 30분)과 Refresh Token rotation/revoke.
- Swagger UI 호환을 위해 CSP의 `script-src`와 `style-src`에는 `'unsafe-inline'`을 허용했다.

## 운영 배포 시 추가 권장

- HTTPS/TLS 종단 설정
- 운영 JWT secret 교체 및 주기적 로테이션
- 관리자 계정 승격 작업에 감사 로그 추가
- S3 버킷 public access block 및 최소 권한 IAM 적용
- RDS SSL 연결과 자동 백업/복구 시나리오 검증
- 정기 의존성 취약점 점검과 부하테스트 도입
