# Pokemo 성능 / 부하 검증

이 문서는 요구사항의 두 가지 비기능 목표를 검증한다.

- 일반 API 응답 3초 이내
- 300~1,000명 초기 사용자 처리

측정값과 추정값을 명확히 구분한다. 측정값은 실제 운영 도메인에서 확인한 수치이며, 용량 추정은 현재 구성/설정 기반의 분석이다. 정식 부하 테스트(k6)는 `scripts/loadtest.js`로 재현할 수 있도록 제공한다.

## 1. 일반 API 응답 3초 이내 (측정)

운영 도메인(`https://pokemo.duckdns.org`) 기준 공개 일반 API 단건 응답 시간:

| 엔드포인트 | 응답 시간 | 비고 |
| --- | --- | --- |
| `GET /api/health` | 2.918초 | 컨테이너/프록시 cold start 영향 포함. warm 상태에서는 더 빠름 |
| `GET /api/notices` | 1.013초 | 공지 목록(캐시 제외 경로) |

- 두 엔드포인트 모두 3초 목표 이내로 측정되었다.
- `/api/health`의 2.9초는 최초 호출 cold start(컨테이너 기동 직후 JIT/커넥션 워밍업) 영향이 크다. 반복 호출 시 수백 ms 수준으로 떨어진다.
- 재측정 명령 예시:

```bash
curl -s -o /dev/null -w "%{time_total}\n" https://pokemo.duckdns.org/api/health
curl -s -o /dev/null -w "%{time_total}\n" https://pokemo.duckdns.org/api/notices
```

## 2. 300~1,000명 초기 사용자 처리 (추정 + 부하 테스트 하니스)

> 상태: 용량 추정 분석과 재현용 부하 테스트 스크립트를 제공한다. 운영 RDS/EC2에 대한 정식 부하 실행은 사전 합의된 시간대에 `scripts/loadtest.js`로 수행한다.

### 2-1. 용량 추정 근거

- "300~1,000명 초기 사용자"는 가입자 규모이며, 동시 접속(concurrent)과는 다르다. 학습 관리 서비스 특성상 동시 활성 사용자는 보통 가입자의 5~15% 수준으로 가정한다. 즉 1,000명 가입 시 피크 동시 사용자는 약 50~150명 수준으로 추정한다.
- 사용자 행동은 읽기 위주(노트/일정/통계 조회)이며 요청 간 think time이 존재해, 사용자당 지속 RPS는 낮다(대략 0.2~1 req/s).
  - 피크 동시 150명 × 1 req/s ≈ 150 RPS 수준을 목표 처리량으로 본다.
- 현재 구성 처리 여력:
  - 단건 일반 API가 warm 상태에서 수백 ms 이내이므로, 톰캣 기본 워커 스레드(200)와 HikariCP 커넥션 풀(기본 10)로 위 목표 RPS 처리에 여유가 있다.
  - 과목/노트/공지 등 조회가 잦은 경로는 Redis 캐시와 페이지네이션/인덱스로 DB 부하를 줄였다.

### 2-2. 권장 검증 절차 (k6)

```bash
# 공개 엔드포인트 기준 300 VU, 1분 부하
k6 run -e BASE_URL=https://pokemo.duckdns.org -e VUS=300 -e DURATION=1m scripts/loadtest.js

# 로그인 사용자 일반 API 포함 (accessToken 주입)
k6 run -e BASE_URL=https://pokemo.duckdns.org -e TOKEN=<accessToken> -e VUS=300 scripts/loadtest.js
```

판정 기준(스크립트 thresholds로 자동 검사):

- `http_req_duration p(95) < 3000ms` — 일반 API 3초 이내 목표
- `http_req_failed rate < 1%` — 안정성

### 2-3. 한계 및 후속

- 정식 부하 테스트 실행 결과는 실행 후 본 문서 표에 측정값으로 추가한다.
- 동시 사용자가 추정 범위를 초과하면 다음을 우선 검토한다.
  - HikariCP `maximum-pool-size` 상향(예: 10 → 20~30)과 RDS `max_connections` 정렬
  - EC2 인스턴스 타입 상향(`t3.small` → `t3.medium` 이상) 또는 backend 컨테이너 수평 확장
  - 조회 캐시 적중률 모니터링 및 TTL 조정
